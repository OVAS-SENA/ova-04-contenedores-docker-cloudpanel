Tema 1: Virtualización Ligera frente a Máquinas Virtuales

Comprende el cambio de paradigma entre la emulación de hardware y el aislamiento de procesos del kernel.

Durante décadas, la virtualización tradicional basada en Hipervisores (como Proxmox VE, VMware ESXi o VirtualBox) fue la solución estándar para consolidar servidores. Sin embargo, cada máquina virtual (VM) requiere un sistema operativo invitado completo, con su propio kernel, módulos, controladores y servicios en segundo plano. Esto ocasiona una duplicación masiva de consumo de memoria RAM, espacio en disco y tiempo de arranque.

🖥️ Máquinas Virtuales Tradicionales (VMs)

Aplicación A + Librerías
SO Invitado A (Kernel completo ~1 GB RAM)
Aplicación B + Librerías
SO Invitado B (Kernel completo ~1 GB RAM)
Hipervisor (Tipo 1 / Tipo 2)
Sistema Operativo Host
Servidor Físico / Hardware Bare Metal

Sobrecarga: Cada VM emula BIOS/UEFI, CPU virtual, controladores de red y un kernel independiente. Arranque en minutos.

🐳 Contenedores Docker (Aislamiento de Kernel)

Contenedor A: App SICAM API + Node.js (42 MB)
Contenedor B: App PostgreSQL 16 (60 MB)
Contenedor C: Nginx Reverse Proxy (15 MB)
Motor Docker Engine / containerd
Kernel Linux Compartido (Namespaces + cgroups v2)
Servidor Físico / Hardware Bare Metal (Ambiente 205)

Eficiencia: No hay SO invitado. Los contenedores son procesos aislados nativos de Linux que comparten el kernel host. Arranque en milisegundos.

Los Dos Pilares del Kernel de Linux que Hacen Posible Docker

🔒 Linux Namespaces (Aislamiento de Visibilidad)

Engañan al proceso para que crea que está solo en la máquina. Los namespaces segregan los recursos del sistema:

  • PID: Los procesos dentro del contenedor tienen su propia numeración iniciando en PID 1.
  • NET: Pila de red independiente (interfaces virtuales eth0, tablas de enrutamiento y puertos).
  • MNT: Puntos de montaje de sistemas de archivos aislados.
  • IPC: Memoria compartida y semáforos interproceso protegidos.
  • UTS: Hostname y nombre de dominio independientes.
  • USER: Mapeo de usuarios para que el UID 0 dentro del contenedor no sea root en el host.
⚖️ Control Groups - cgroups v2 (Cuotas y Límites)

Regulan y auditan el consumo de recursos de hardware de los procesos para evitar que un contenedor acapare el servidor:

  • Memoria RAM: Límite máximo (ej. --memory="512m") y prevención del OOM Killer en el sistema anfitrión.
  • CPU: Asignación de núcleos dedicados (--cpuset-cpus) o peso relativo de tiempo de procesamiento (--cpus="1.5").
  • Block I/O: Restricción de velocidad de lectura y escritura en discos SSD/NVMe.
  • Network: Clasificación y limitación de ancho de banda por socket.

Sistema de Archivos en Capas (Overlay2 / UnionFS)

Las imágenes de Docker no son archivos monolíticos; son un apilamiento de capas de sólo lectura (Read-Only Layers) inmutables basadas en SHA-256. Cuando lanzas un contenedor a partir de una imagen, Docker añade en la cima una delgada capa de lectura y escritura (Read-Write Container Layer).

⚡
Estrategia Copy-on-Write (CoW)
Si 20 aprendices en el Ambiente 205 lanzan 20 contenedores de la imagen node:20-alpine, los 20 contenedores comparten en memoria la misma imagen base de 45 MB. Solo cuando un contenedor modifica un archivo existente, el kernel copia dicho archivo hacia su capa de lectura/escritura particular. ¡Esto ahorra gigabytes de almacenamiento y memoria en los servidores del aula!

Tema 2: Docker Engine, Dockerfiles y Docker Compose

Domina la construcción de artefactos reproducibles, técnicas de optimización y orquestación multicontenedor.

El Docker Engine es una suite cliente-servidor compuesta por el demonio dockerd, la interfaz estándar containerd, el ejecutor de bajo nivel runc (cumpliendo la especificación OCI) y el CLI de comandos accesible mediante el socket UNIX /var/run/docker.sock.

Comandos Esenciales del Flujo de Trabajo DevOps

📋 1. Gestión del Ciclo de Vida de Contenedores ▾
bash · terminal ambiente 205
# Ejecutar un contenedor en segundo plano (-d) con nombre y puertos mapeados:
sena@nodo205:~$ docker run -d --name sicam-api -p 3000:3000 --restart always node:20-alpine
# Listar contenedores en ejecución:
sena@nodo205:~$ docker ps
# Ver consumo en tiempo real de CPU, Memoria e I/O de todos los contenedores:
sena@nodo205:~$ docker stats
# Detener y reiniciar un contenedor:
sena@nodo205:~$ docker stop sicam-api && docker restart sicam-api
🔍 2. Inspección, Logs y Depuración Interactiva ▾
bash · inspección de contenedores
# Seguir en vivo los logs de la aplicación (--tail para limitar líneas):
sena@nodo205:~$ docker logs -f --tail 100 sicam-api
# Abrir una terminal interactiva dentro del contenedor:
sena@nodo205:~$ docker exec -it sicam-api /bin/sh
# Inspeccionar la configuración JSON completa (redes, IP interna, volúmenes):
sena@nodo205:~$ docker inspect sicam-api | grep -i IPAddress
🧹 3. Mantenimiento y Limpieza de Recursos del Sistema ▾
bash · docker system prune
# Ver cuánto espacio en disco ocupa Docker en el nodo:
sena@nodo205:~$ docker system df
# Limpiar contenedores detenidos, redes sin uso e imágenes huérfanas:
sena@nodo205:~$ docker system prune -a --volumes

Anatomía de un Dockerfile Optimizado con Multi-Stage Build

Uno de los errores más comunes en aprendices novatos es incluir compiladores, herramientas de desarrollo (SDKs, git, gcc, devDependencies de npm) en la imagen final que irá a producción. La técnica Multi-Stage Build divide el proceso en dos o más etapas: una etapa de construcción (builder) y una etapa final limpia (production runner).

Dockerfile · Proyecto SICAM (Node.js + TypeScript + Alpine)
# ==========================================
# ETAPA 1: Compilación de dependencias (Builder)
# ==========================================
FROM node:20-alpine AS builder
WORKDIR /app
# Aprovechar el caché de capas copiando primero package.json
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --production

# ==========================================
# ETAPA 2: Imagen Final Mínima y Segura
# ==========================================
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
# Crear usuario sin privilegios por seguridad (evitar root)
RUN addgroup -g 1001 -S sena && adduser -V -D -u 1001 -G sena senauser
# Copiar SOLO los artefactos compilados de la Etapa 1
COPY --from=builder --chown=senauser:sena /app/node_modules ./node_modules
COPY --from=builder --chown=senauser:sena /app/dist ./dist
COPY --from=builder --chown=senauser:sena /app/package.json ./package.json

USER senauser
EXPOSE 3000
CMD ["node", "dist/server.js"]

Orquestación con Docker Compose (docker-compose.yml)

En proyectos del mundo real, una aplicación nunca corre aislada: necesita una base de datos relacional, un broker de mensajería para sensores IoT o una caché rápida. Docker Compose permite definir y ejecutar arquitecturas multicontenedor mediante un único archivo declarativo en formato YAML.

Reglas de Oro en Compose v2 para los Aprendices:
  1. Healthchecks Obligatorios: Configura siempre un healthcheck en el servicio de base de datos para que el backend espere con depends_on: { db: { condition: service_healthy } }.
  2. Named Volumes para Persistencia: Nunca guardes información transaccional dentro del contenedor. Declara un volumen administrado (ej. postgres_data) para que los datos sobrevivan a reinicios y actualizaciones.
  3. Redes Privadas Puente (Bridge Networks): Aísla la base de datos de internet; solo el Reverse Proxy debe tener expuesto el puerto 80 o 443 al mundo exterior.

Tema 3: Gestión de Servidores y Despliegue con CloudPanel y Dokploy

Aprende a gestionar el servidor Ubuntu del Ambiente 205 con paneles ligeros de última generación.

Tradicionalmente, administrar servidores requería paneles pesados y privativos como cPanel o Plesk, que consumían más de 2 GB de RAM solo en su panel de administración. En el Ambiente 205 implementamos alternativas modernas, de código abierto y alto rendimiento: CloudPanel (orientado a hosting web Nginx de ultra-baja latencia) y Dokploy (una plataforma PaaS tipo Vercel/Heroku auto-hospedada sobre Docker).

Características Clave de CloudPanel

  • Stack de Rendimiento: Motor Nginx optimizado, PHP-FPM multiversión (8.1, 8.2, 8.3), Node.js, Python y MySQL/MariaDB.
  • SSL Automático: Emisión e instalación de certificados Let's Encrypt con un solo clic y renovación desatendida mediante cron.
  • Seguridad de Aislamiento: Cada sitio web corre bajo su propio usuario del sistema operativo Linux sin privilegios sudo.
  • Reverse Proxy Nativo: Permite configurar fácilmente un proxy inverso hacia aplicaciones Node.js, Python o contenedores Docker en ejecución local.
Flujo de Configuración de un Reverse Proxy en CloudPanel:
1. Crear sitio tipo Reverse Proxy con el dominio (ej. sicam.centrominero.edu.co).
2. Establecer la URL de destino al contenedor interno: http://127.0.0.1:3000.
3. Activar la casilla de verificación Enable SSL para cifrado HTTPS seguro.
Bloque de Configuración Nginx para Despliegues en Contenedores:
/etc/nginx/sites-enabled/sicam.conf
server {
  listen 80;
  server_name sicam.centrominero.edu.co;
  return 301 https://$host$request_uri; # Forzar redirección HTTPS
}

server {
  listen 443 ssl http2;
  server_name sicam.centrominero.edu.co;
  # Certificados TLS gestionados automáticamente por CloudPanel
  ssl_certificate /etc/letsencrypt/live/sicam/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/sicam/privkey.pem;

  location / {
    proxy_pass http://127.0.0.1:3000; # Redirección al contenedor Docker del aprendiz
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    # Soporte para WebSockets y Server-Sent Events
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
  }
}

Dokploy: La Nube Privada del Centro Minero

Dokploy es una plataforma de despliegue continuo que corre directamente sobre el motor Docker de nuestro nodo Ubuntu. Permite a los aprendices trabajar como en empresas de tecnología de primer nivel (como Vercel, Netlify o AWS ECS), pero 100% alojado localmente en el Centro Minero sin costos de nube.

  • Git Webhooks: Cada vez que el aprendiz hace git push a GitHub o al servidor Gitea del aula, Dokploy reconstruye la imagen automáticamente.
  • Despliegue Zero-Downtime: Levanta el nuevo contenedor y solo conmuta el tráfico cuando el healthcheck pasa con éxito.
  • Traefik Integrado: Enrutamiento dinámico que detecta automáticamente los contenedores levantados sin reiniciar el proxy.
Pipeline Típico de un Aprendiz ADSO en Dokploy:
1. Aprendiz edita código en VS Code.
2. git commit -m "feat: login RFID mina" && git push.
3. Webhook activa Dokploy en Nodo 205.
4. Dokploy ejecuta docker build con Dockerfile.
5. Se realizan pruebas unitarias automáticas.
6. Traefik actualiza la ruta y la app queda en vivo.

Caso de Estudio 1

SICAM: Sistema de Control de Acceso a Mina Didáctica

En Producción Activa

El proyecto SICAM regula el ingreso y salida de instructores, aprendices y cuadrillas de salvamento minero en la bocamina didáctica de Morcá. Utiliza hardware IoT (microcontroladores ESP32 con lectores RFID de largo alcance) interconectados con una arquitectura en contenedores Docker.

📡 Gateway IoT & Broker MQTT
Contenedor eclipse-mosquitto ligero que recibe las lecturas de los torniquetes cada 50 milisegundos con protocolo QoS 1 garantizado.
🧠 Backend API (Node / Express)
Contenedor que procesa los tokens de autenticación, verifica el estado del seguro de riesgos laborales y autoriza la apertura del solenoide.
🗄️ PostgreSQL + Named Volume
Base de datos relacional con volumen persistente sicam_db_data que almacena el censo en tiempo real del personal bajo tierra.
🔒
Aislamiento de Redes en el Proyecto SICAM
Para cumplir con estándares de ciberseguridad industrial, la base de datos PostgreSQL y el broker MQTT se conectan a una red interna aislada mine_internal_net (sin mapeo de puertos hacia el host). Solo el reverse proxy Nginx tiene salida a la red institucional del Centro Minero para servir el panel de monitoreo a los instructores.
Caso de Estudio 2

SIPAC: Sistema de Información para Producción y Aprendizaje

Despliegue Continuo con Dokploy

El SIPAC gestiona los laboratorios de ensayo de carbones y suelos del Centro Minero, registrando análisis de humedad, porcentaje de cenizas y poder calorífico de las muestras minerales. Está desplegado con un stack MERN/LEMP multicontenedor orquestado por Docker Compose.

⚡ Despliegue Automatizado con Git
Los aprendices integran ramas feature/* hacia main; el servidor Dokploy compila el Dockerfile multi-stage y actualiza la aplicación en menos de 40 segundos sin interrumpir el trabajo del laboratorio.
💾 Estrategia de Respaldo Automatizado
Un contenedor auxiliar pg-dump-cron realiza copias de seguridad cada medianoche hacia una unidad de almacenamiento NAS protegida contra cortes de energía en la subestación.

Síntesis Conceptual y Decálogo DevOps SENA

Estructura integral de conocimientos para el desarrollo y despliegue de aplicaciones modernas.

Mapa de Capas de la Pila de Contenedores

Capa 1: Infraestructura y Kernel Host (Ambiente 205)
Servidor Ubuntu 24.04 LTS bare-metal con soporte de cgroups v2 y namespaces activos.
Capa 2: Motor de Contenedores (Docker Engine & containerd)
Gestión del demonio dockerd, almacenamiento de capas con overlay2 y redes virtuales tipo bridge.
Capa 3: Empaquetamiento y Orquestación (Dockerfile & Compose)
Construcción multi-stage, salud de contenedores (healthchecks), volúmenes persistentes y redes privadas.
Capa 4: Plataforma de Gestión y Despliegue (CloudPanel & Dokploy)
Reverse Proxy Nginx, certificados SSL automáticos y pipelines CI/CD vía Git Webhooks.
Capa 5: Proyectos Formativos Productivos (SICAM & SIPAC)
Soluciones aplicadas a la Mina Didáctica de Morcá, laboratorios de carbones y control de acceso seguro.

El Decálogo del Desarrollador DevOps SENA

1. Nunca en Producción como Root: Declara siempre un usuario sin privilegios (USER senauser) en tu Dockerfile.
2. Imágenes Ultraligeras: Emplea imágenes Alpine o Distroless con Multi-Stage Build para minimizar la superficie de vulnerabilidades.
3. Sin Datos en Contenedores: Separa el estado efímero del persistente mediante Named Volumes administrados.
4. Healthchecks Activos: No asumas que un contenedor está listo solo porque inició su proceso principal. Monitorea su salud.
5. Dependencias Ordenadas: Utiliza depends_on condicionado al estado saludable (service_healthy) de la base de datos.
6. Redes Privadas Segmentadas: Mantén las bases de datos en redes internas cerradas y expón únicamente el proxy público.
7. Variables de Entorno Seguras: Nunca quemes contraseñas o llaves API en el código ni en el Dockerfile; usa archivos .env.
8. Límites de Recursos Explícitos: Fija límites de memoria y CPU en cada servicio para evitar caídas generales del servidor.
9. Despliegue Continuo Automatizado: Configura Webhooks en Dokploy o CloudPanel para despliegues trazables desde Git.
10. Limpieza Sistemática: Realiza mantenimiento preventivo con docker system prune para no saturar el almacenamiento del aula.

Glosario Técnico de Términos DevOps & Contenedores

Escribe en el buscador para filtrar términos técnicos en tiempo real.

Control Groups (cgroups v2): Característica del kernel de Linux que permite limitar, contabilizar y aislar el uso de recursos de hardware (CPU, memoria, E/S de disco, red) de una colección de procesos.
Linux Namespaces: Mecanismo de virtualización ligera del kernel Linux que proporciona aislamiento de visibilidad a los procesos (PID, red, puntos de montaje, IPC, usuario y hostname).
Overlay2: Controlador de almacenamiento (storage driver) predeterminado en Docker sobre Linux que implementa un sistema de archivos en capas apiladas mediante UnionFS con estrategia Copy-on-Write.
Docker Daemon (dockerd): Proceso de servicio en segundo plano persistente que administra contenedores, imágenes, redes y volúmenes en el sistema anfitrión.
Multi-Stage Build: Metodología de construcción en Dockerfile que utiliza múltiples instrucciones FROM temporales para compilar dependencias pesadas y copiar únicamente los artefactos finales a una imagen mínima.
Named Volume (Volumen con Nombre): Espacio de almacenamiento gestionado nativamente por Docker en el host (/var/lib/docker/volumes/) que persiste los datos más allá del ciclo de vida del contenedor.
Bind Mount: Montaje directo de un directorio o archivo específico de la máquina anfitriona dentro del contenedor, comúnmente empleado en entornos de desarrollo local para hot-reload.
Bridge Network: Red de puente virtual privada creada por Docker que permite a los contenedores conectados comunicarse entre sí mediante resolución interna de nombres DNS (nombre de servicio).
Healthcheck: Sonda periódica de verificación definida en el contenedor para evaluar si la aplicación interior está realmente respondiendo y lista para recibir tráfico.
Docker Compose: Herramienta para definir y ejecutar aplicaciones Docker multicontenedor mediante un archivo declarativo YAML (docker-compose.yml).
CloudPanel: Panel de control para servidores Linux Ubuntu optimizado con PHP, Node.js y Nginx para hospedaje web de ultra-alta velocidad y consumo mínimo de recursos.
Dokploy: Plataforma PaaS de código abierto auto-alojada que automatiza el despliegue de aplicaciones y bases de datos sobre Docker mediante Git Webhooks y Traefik.
Reverse Proxy (Proxy Inverso): Servidor intermedio (como Nginx) que recibe peticiones externas en puertos estándar 80/443 y las reenvía a los puertos internos donde corren los microservicios.
Let's Encrypt / Certbot: Autoridad certificadora gratuita y automatizada que emite certificados digitales X.509 para habilitar el cifrado TLS/HTTPS seguro.
Git Webhook: Mecanismo de notificación HTTP POST disparado por un repositorio Git al recibir un nuevo commit, activando automáticamente el pipeline de despliegue continuo.
SICAM: Sistema de Control de Acceso a Mina Didáctica, proyecto formativo del Centro Minero que integra sensores IoT RFID con microservicios en Docker.
SIPAC: Sistema de Información para Producción y Aprendizaje en Centros Mineros, plataforma de laboratorios de carbón y suelos desplegada en el Ambiente 205.
Container Image Layer: Capa inmutable de sólo lectura identificada por un hash criptográfico SHA-256 que compone secuencialmente una imagen de Docker.
